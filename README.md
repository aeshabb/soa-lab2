# СОА — лабораторная работа №2

Реализация варианта **Ticket / Booking** из [первой лабораторной](https://github.com/F4d4/ITMO_University/tree/main/soa/lab1). Исходные OpenAPI 3.0.3 спецификации сохранены без изменения в `spec/`. Числовой номер варианта в исходных файлах не указан.

Минимальный стек: Java 17, Jakarta REST (JAX-RS), JSON-P, JDBC, PostgreSQL, Maven. Ticket Service работает на **WildFly 35.0.1.Final**, Booking Service и клиент — на **Payara 6.2025.1**. Клиент написан на HTML/CSS/JavaScript без отдельной сборки и внешних библиотек и включён в WAR второго сервиса.


## Развёрнуто на Helios

Каталог: `~/soa-lab2` аккаунта `s408256`.

| Компонент | Адрес на сервере |
|---|---|
| Первый сервис | `https://helios.cs.ifmo.ru:28256/tickets` |
| Второй сервис | `https://helios.cs.ifmo.ru:29256/booking/...` |
| Веб-клиент | `https://helios.cs.ifmo.ru:29256/` |

Прямое внешнее подключение к этим портам из проверенной сети не проходит. Для доступа откройте SSH-туннель на своём компьютере и оставьте команду работающей:

```sh
ssh -p 2222 -N \
  -L 28256:127.0.0.1:28256 \
  -L 29256:127.0.0.1:29256 \
  s408256@helios.cs.ifmo.ru
```

После этого откройте **[клиент](https://localhost:29256/)**. Первый API доступен по `https://localhost:28256/tickets`, второй — по `https://localhost:29256/booking/...`. HTTPS сохраняется внутри SSH-туннеля.

Сертификаты самоподписанные, поэтому браузер покажет предупреждение при первом открытии. Публичные сертификаты развёртывания находятся в `certs/`. Для проверок через curl используйте `--cacert certs/wildfly.crt` или `--cacert certs/payara.crt`. Приватные ключи, пароли SSH и настройки с паролями в репозиторий не включены. Сертификаты действуют 365 дней с момента установки; при новой установке создаются заново.

## Возможности API и клиента

| Метод и путь | Действие |
|---|---|
| `GET /tickets` | Фильтрация, сортировка и постраничная выборка |
| `POST /tickets` | Создание билета и места, автоматические ID и дата |
| `GET /tickets/{id}` | Получение по ID |
| `PUT /tickets/{id}` | Полная замена изменяемых данных, сохранение ID и даты |
| `DELETE /tickets/{id}` | Удаление свободного билета |
| `DELETE /tickets/price/{price}` | Удаление одного свободного билета с заданной ценой |
| `GET /tickets/price/average` | Средняя цена; для пустой коллекции — 0 |
| `GET /tickets/comment/min` | Билет с минимальным комментарием; null не участвует |
| `POST /booking/sell/vip/{ticket-id}/{person-id}` | VIP-копия с удвоенной ценой и назначенным человеком |
| `POST /booking/person/{person-id}/cancel` | Снятие всех бронирований человека, без удаления билетов |

Фильтры объединяются «И». Поля: `id`, `name`, `coordinateX`, `coordinateY`, `creationDate`, `price`, `comment`, `type`, `venueId`, `venueName`, `venueCapacity`, `venueType`, `personId`. Для строк `name`, `comment`, `venueName` есть `Contains` без учёта регистра; для чисел и даты — включительные `From`/`To`. В `sort` поля перечисляются через запятую, `-` задаёт убывание; например, `sort=-price,name`. `page` начинается с 1, `size` — от 1 до 100 (по умолчанию 20).

Даты имеют формат `dd.MM.yyyy HH:mm:ss`, время сервера. Типы билетов: `VIP`, `USUAL`, `BUDGETARY`, `CHEAP`; типы мест: `BAR`, `CINEMA`, `MALL` или null. Имя и название места не пустые, цена и вместимость положительные; координата X — int32, Y — конечное double. Необязательные поля поддерживают null; пустой комментарий является допустимой строкой.

Клиент содержит таблицу всех полей, редактор билета, добавляемые фильтры и строки сортировки, выбор страницы и все дополнительные операции обоих сервисов. Ошибки выводятся рядом с отправленной формой с HTTP-кодом и нарушенными ограничениями; неверные поля редактора подсвечиваются и получают пояснения под ними. Клиент вызывает `/client-api/tickets/...` на Payara; этот прокси обращается к WildFly **по HTTPS** с проверкой сертификата и имени узла. Booking Service также вызывает первый сервис по HTTPS и не хранит свою коллекцию.

Ошибки имеют поля `timestamp`, `status`, `error`, `message`, `path`, при валидации — `violations`. Неверный синтаксис — 400, отсутствующий билет — 404, конфликт — 409, неверный Content-Type — 415, нарушение ограничений — 422, недоступное хранилище — 503. Второй сервис возвращает 502 при недоступности или некорректном ответе первого и 504 при тайм-ауте. Изменения одного билета защищены от конкурирующих PUT во время обработки запроса. Отмена нескольких бронирований выполняется последовательными REST-вызовами, без распределённой транзакции.

## Сборка и установка

```sh
mvn package
```

Результат: `ticket-service/target/ticket-service.war` и `booking-service/target/booking-service.war`.

Первое развёртывание или обновление:

```sh
bash deploy/upload.sh s408256@helios.cs.ifmo.ru
```

Скрипт собирает WAR локально, передаёт их по SSH и устанавливает отдельные серверы в `~/soa-lab2/runtime`. На Helios используются `/usr/local/openjdk17` и `/usr/local/bin/python3.11`; требуются curl, tar, openssl. Архивы распаковываются из потока, чтобы не занимать лишнюю дисковую квоту. HTTP-слушатели приложений удалены; доступ к REST API по HTTP запрещён. Администрирование доступно только через loopback на портах 28290 и 29248.

На сервере:

```sh
bash ~/soa-lab2/deploy/stop.sh
bash ~/soa-lab2/deploy/start.sh
```

Ticket Service сохраняет билеты в PostgreSQL: сервер `pg:5432`, база `studs`, схема `s408256`. В таблице `soa_lab2_tickets` находятся отдельные столбцы `id`, `name`, `coordinate_x`, `coordinate_y`, `creation_date`, `price`, `comment`, `type`, `venue_id`, `person_id`. Площадки хранятся в `soa_lab2_venues` (`id`, `name`, `capacity`, `type`) и связаны с билетами внешним ключом `venue_id`. JSON/JSONB-столбцов нет. Типы столбцов и CHECK-ограничения соответствуют модели; дата хранится как `timestamp`, цена — `real`, координата Y — `double precision`, необязательные поля — SQL NULL. Таблица `soa_lab2_state` хранит следующие ID билета и площадки. Изменение билета, площадки и счётчиков выполняется в одной JDBC-транзакции; коллекция в памяти обновляется после успешного COMMIT и загружается из БД при запуске. Данные переживают остановку, повторный запуск и обновление WAR.

`deploy/configure-postgres.py` создаёт отдельные таблицы в текущей схеме пользователя, один раз переносит прежний `tickets.json` и оставляет его резервную копию `tickets-before-postgres.json`. При обновлении промежуточного JSONB-хранилища данные переносятся в обычные столбцы одной транзакцией, а резервная копия сохраняется в `.runtime/tickets-before-relational.json`. Скрипт запускается при остановленном Ticket Service. После переноса сервис JSON-файл не обновляет. PostgreSQL JDBC-драйвер читает пароль из `~/.pgpass`; пароль не копируется в проект. Подключение задаётся переменными `TICKET_DATABASE_URL` и `TICKET_DATABASE_USER` в закрытом файле `.runtime/settings.sh`. Для другого аккаунта используются его схема и `~/.pgpass`; при необходимости перед настройкой можно задать `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`.

Посмотреть билеты через `psql` на Helios:

```sh
psql -h pg -d studs -U s408256
```

```sql
SELECT t.*, v.name AS venue_name, v.capacity, v.type AS venue_type
FROM s408256.soa_lab2_tickets t
JOIN s408256.soa_lab2_venues v ON v.id = t.venue_id
ORDER BY t.id;
```

Логи: `~/soa-lab2/.runtime/wildfly.log` и `~/soa-lab2/runtime/payara6/glassfish/domains/domain1/logs/server.log`. Параметры и сгенерированные хранилища ключей находятся в закрытом каталоге `.runtime`, права — только владельцу. Автоматический запуск после перезагрузки Helios не настраивается.

Для другого аккаунта при первой установке задайте свободные порты переменными `TICKET_HTTPS_PORT`, `BOOKING_HTTPS_PORT`, `WILDFLY_ADMIN_PORT`, `PAYARA_ADMIN_PORT` перед запуском `install.sh` и измените параметры туннеля.

## Проверки

На реальных серверах пройдено **205 HTTP-проверок**: CRUD, сортировка по всем полям в обоих направлениях, совместная фильтрация, страницы, дополнительные операции, VIP-копия, ошибки 400/404/409/415/422 и отмена **103 бронирований** с повторным идемпотентным вызовом. Проверяются строгий JSON без лишних данных после объекта, ссылка Location на созданную VIP-копию в первом сервисе и передача закодированных путей через прокси. Скрипт выбирает незанятые цены и ID человека и удаляет только созданные им тестовые билеты.

Отдельно проверены повторный запуск и остановка, сохранение билета после перезапуска WildFly и JSON-ответ 502 при остановленном первом сервисе. HTTPS проверен с сертификатами из репозитория и проверкой имени узла; незашифрованные HTTP-запросы отклоняются. Клиентские DOM-сценарии с настоящим HTTPS API проверяют создание, чтение, обновление, ошибки рядом с формами, подсветку неверных полей, фильтр, сортировку, VIP-продажу, отмену брони, среднюю цену и удаление. Очень маленькие положительные цены отображаются в научной записи и не округляются до нуля.

Через открытый SSH-туннель:

```sh
python3 tests/api_smoke.py \
  --ticket-url https://localhost:28256 \
  --booking-url https://localhost:29256 \
  --ticket-cert certs/wildfly.crt \
  --booking-cert certs/payara.crt
```

## Структура

```text

ticket-service/   JAX-RS API, выборки, PostgreSQL-хранилище
booking-service/  JAX-RS API, HTTPS-клиент первого сервиса, веб-клиент
spec/             исходные спецификации первой лабораторной
deploy/           установка, запуск, остановка и передача WAR
tests/            интеграционная проверка API
certs/            публичные сертификаты текущего развёртывания
```
