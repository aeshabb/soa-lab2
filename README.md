# СОА — лабораторная работа №2

Реализация варианта **Ticket / Booking** из [первой лабораторной](https://github.com/F4d4/ITMO_University/tree/main/soa/lab1). Исходные OpenAPI 3.0.3 спецификации сохранены без изменения в `spec/`. Числовой номер варианта в исходных файлах не указан.

Минимальный стек: Java 17, Jakarta REST (JAX-RS), JSON-P, JDBC, PostgreSQL, Maven. Ticket Service и клиент работают на **WildFly 35.0.1.Final**, Booking Service — на **Payara 6.2025.1**. Клиент написан на HTML/CSS/JavaScript без отдельной сборки и внешних библиотек и включён в WAR первого сервиса.


## Развёрнуто на Helios

Каталог: `~/soa-lab2` аккаунта `s408256`.

| Компонент | Адрес на сервере |
|---|---|
| Первый сервис | `https://helios.cs.ifmo.ru:28256/tickets` |
| Второй сервис | `https://helios.cs.ifmo.ru:29256/booking/...` |
| Веб-клиент | `https://helios.cs.ifmo.ru:28256/` |

В сети, из которой доступен Helios на порту 28256, можно ввести `helios.cs.ifmo.ru:28256` без `https://`: HTTP-запрос получит **308 Permanent Redirect** на HTTPS с сохранением пути, параметров и метода. Перенаправление настроено на сервере и работает для всех посетителей. По HTTP клиент и API не выдаются. Предупреждение о самоподписанном сертификате при первом HTTPS-подключении остаётся.

Если прямое подключение к этим портам из вашей сети не проходит, откройте SSH-туннель на своём компьютере и оставьте команду работающей:

```sh
ssh -p 2222 -N \
  -L 28256:127.0.0.1:28256 \
  -L 29256:127.0.0.1:29256 \
  s408256@helios.cs.ifmo.ru
```

После этого откройте **[клиент](https://localhost:28256/)**. Первый API доступен по `https://localhost:28256/tickets`, второй — по `https://localhost:29256/booking/...`. HTTPS сохраняется внутри SSH-туннеля.

Сертификаты самоподписанные, поэтому браузер покажет предупреждение при первом открытии. Публичные сертификаты развёртывания находятся в `certs/`. Для проверок через curl используйте `--cacert certs/wildfly.crt` или `--cacert certs/payara.crt`. Приватные ключи, пароли SSH и настройки с паролями в репозиторий не включены. Сертификаты действуют 365 дней с момента установки.

## Возможности API и клиента

| Метод и путь | Действие |
|---|---|
| `GET /tickets` | Фильтрация, сортировка и постраничная выборка |
| `POST /tickets` | Создание билета и места, автоматические ID и дата |
| `GET /tickets/{id}` | Получение по ID |
| `PUT /tickets/{id}` | Полная замена изменяемых данных, сохранение ID и даты |
| `DELETE /tickets/{id}` | Удаление свободного билета |
| `DELETE /tickets/price/{price}` | Удаление одного свободного билета с заданной ценой |
| `GET /tickets/price/average` | Средняя цена; для пустой коллекции — 0 |
| `GET /tickets/comment/min` | Билет с минимальным комментарием; null не участвует |
| `POST /booking/sell/vip/{ticket-id}/{person-id}` | VIP-копия с удвоенной ценой и назначенным человеком |
| `POST /booking/person/{person-id}/cancel` | Снятие всех бронирований человека, без удаления билетов |

Фильтры объединяются «И». Поля: `id`, `name`, `coordinateX`, `coordinateY`, `creationDate`, `price`, `comment`, `type`, `venueId`, `venueName`, `venueCapacity`, `venueType`, `personId`. Для строк `name`, `comment`, `venueName` есть `Contains` без учёта регистра; для чисел и даты — включительные `From`/`To`. В `sort` поля перечисляются через запятую, `-` задаёт убывание; например, `sort=-price,name`. `page` начинается с 1, `size` — от 1 до 100 (по умолчанию 20).

Даты имеют формат `dd.MM.yyyy HH:mm:ss`, время сервера. Типы билетов: `VIP`, `USUAL`, `BUDGETARY`, `CHEAP`; типы мест: `BAR`, `CINEMA`, `MALL` или null. Имя и название места не пустые, цена и вместимость положительные; координата X — int32, Y — конечное double. Необязательные поля поддерживают null; пустой комментарий является допустимой строкой.

Клиент содержит таблицу всех полей, редактор билета, добавляемые фильтры и строки сортировки, выбор страницы и все дополнительные операции обоих сервисов. Ошибки выводятся рядом с отправленной формой с HTTP-кодом и нарушенными ограничениями; неверные поля редактора подсвечиваются и получают пояснения под ними. Клиент загружается с WildFly и вызывает `/tickets/...` напрямую. Для VIP-продажи и отмены бронирований он вызывает `/client-api/booking/...` на WildFly; этот прокси обращается к Payara **по HTTPS** с проверкой сертификата и имени узла. Booking Service вызывает REST API первого сервиса по HTTPS и не хранит свою коллекцию. При недоступности Payara прокси возвращает 502, при тайм-ауте — 504.

Ошибки имеют поля `timestamp`, `status`, `error`, `message`, `path`, при валидации — `violations`. Неверный синтаксис — 400, отсутствующий билет — 404, конфликт — 409, неверный Content-Type — 415, нарушение ограничений — 422, недоступное хранилище — 503. Второй сервис возвращает 502 при недоступности или некорректном ответе первого и 504 при тайм-ауте. Изменения одного билета защищены от конкурирующих PUT во время обработки запроса. Отмена нескольких бронирований выполняется последовательными REST-вызовами, без распределённой транзакции.

## Сборка и запуск

```sh
mvn package
```

Результат: `ticket-service/target/ticket-service.war` и `booking-service/target/booking-service.war`.

На Helios серверы уже установлены в `~/soa-lab2/runtime`, готовые WAR находятся в `~/soa-lab2/artifacts`. Для входа и запуска обоих сервисов:

```sh
ssh -p 2222 s408256@helios.cs.ifmo.ru
bash ~/soa-lab2/deploy/start.sh
```

На компьютере с настроенным SSH-ключом и алиасом достаточно `ssh helios`. После ручной остановки сервисов повторно выполните ту же команду запуска. Поиск PID и остановка процессов выполняются вручную. Если оба сервиса уже доступны, повторный запуск скрипта не перезапускает их. Скрипт сразу сообщает этап запуска и повторяет сообщение во время ожидания; при завершении WildFly во время запуска сразу выдаёт ошибку и путь к журналу. Проверки HTTPS имеют ограничение времени. Настройки JVM задаются внутри скрипта: внешние `_JAVA_OPTIONS` и `JDK_JAVA_OPTIONS` не влияют на запуск серверов.

`deploy/start.sh` — единственный скрипт управления сервисами. Он задаёт `BOOKING_SERVICE_URL` и `BOOKING_CERTIFICATE` для HTTPS-вызовов Payara из WildFly. Он использует существующие настройки `.runtime/settings.sh`, сертификаты, WAR и установленные серверы, а также запускает nginx и проверяет HTTP-редирект и публичный HTTPS-вход. Администрирование серверов доступно только через loopback на портах 28290 и 29248.

nginx установлен в `runtime/nginx`, шаблон конфигурации хранится в `deploy/nginx.conf`. Публичный порт **28256** принимает TCP-соединения: модуль `stream_ssl_preread` направляет TLS в WildFly на **127.0.0.1:28257**, а обычный HTTP — на обработчик редиректа **127.0.0.1:28258**. Оба внутренних порта слушают только loopback. TLS завершается в WildFly; nginx не расшифровывает запросы и не хранит закрытый ключ. Payara продолжает использовать прежний HTTPS-адрес Ticket API на порту 28256. Подход основан на [выборе TCP-сервера по протоколу в nginx](https://nginx.org/en/docs/stream/ngx_stream_ssl_preread_module.html).

| Состояние | Клиент и Ticket API на WildFly | Booking API на Payara |
|---|---|---|
| Оба сервера работают | Все операции доступны; изменения записываются в PostgreSQL | Штатные ответы |
| Payara завершён через `kill` | Страница, таблица и операции Ticket работают; VIP и отмена показывают ошибку 502 | Соединение отклоняется |
| WildFly завершён через `kill` | Страница и Ticket API недоступны | Сервер продолжает принимать запросы; операции, требующие Ticket, возвращают HTTP 502 |
| Оба завершены | TLS-соединение завершается без ответа приложения | Соединение отклоняется |

Серверы автоматически друг друга не завершают и не перезапускают. Остановка Payara не мешает открыть или обновить страницу клиента на порту 28256. При остановке WildFly клиент недоступен, но до Payara на порту 29256 можно обратиться через curl и получить HTTP-ошибку зависимости.

nginx — отдельный процесс входного порта. Если WildFly остановлен, HTTP-редирект может продолжать отвечать, но загрузить клиент или Ticket API по HTTPS нельзя: nginx не содержит их копии. Останавливать nginx для проверки отказов WildFly и Payara не требуется. Если завершить сам nginx, публичный порт 28256 станет недоступен; `start.sh` снова запустит его.

API и клиент отправляют `Cache-Control: no-store`, запросы `fetch` не используют
кэш. Клиент очищает старый результат перед новым действием, убирает неактуальную
таблицу при неудачной загрузке и ограничивает ожидание запроса 30 секундами.
Сообщения об отказах рассчитаны на пользователя: например, «Ошибка 502. Сервис
временно недоступен. Попробуйте ещё раз позже». Реальный HTTP-код сохраняется,
а названия серверов, SSH и внутренние причины в интерфейсе не показываются.
При обрыве соединения HTTP-ответа нет, поэтому выдуманный код не выводится.
При обрыве изменяющего запроса результат может быть неизвестен — автоматического
повтора нет. Если запись подтверждена, а последующее обновление таблицы не удалось,
подтверждение записи сохраняется, ошибка обновления показывается отдельно.

Ticket Service сохраняет билеты в PostgreSQL: сервер `pg:5432`, база `studs`, схема `s408256`. В таблице `soa_lab2_tickets` находятся отдельные столбцы `id`, `name`, `coordinate_x`, `coordinate_y`, `creation_date`, `price`, `comment`, `type`, `venue_id`, `person_id`. Площадки хранятся в `soa_lab2_venues` (`id`, `name`, `capacity`, `type`) и связаны с билетами внешним ключом `venue_id`. JSON/JSONB-столбцов нет. Типы столбцов и CHECK-ограничения соответствуют модели; дата хранится как `timestamp`, цена — `real`, координата Y — `double precision`, необязательные поля — SQL NULL. Таблица `soa_lab2_state` хранит следующие ID билета и площадки. Изменение билета, площадки и счётчиков выполняется в одной JDBC-транзакции; коллекция в памяти обновляется после успешного COMMIT и загружается из БД при запуске. Данные переживают остановку, повторный запуск и обновление WAR.

Схема таблиц сохранена в `deploy/postgres.sql`; на Helios таблицы уже созданы и содержат данные. PostgreSQL JDBC-драйвер читает пароль из `~/.pgpass`; пароль не копируется в проект. Подключение задаётся переменными `TICKET_DATABASE_URL` и `TICKET_DATABASE_USER` в закрытом файле `.runtime/settings.sh`. Резервные копии прежнего хранилища остаются на сервере; рабочие данные хранятся в PostgreSQL.

Посмотреть билеты через `psql` на Helios:

```sh
psql -h pg -d studs -U s408256
```

```sql
SELECT t.*, v.name AS venue_name, v.capacity, v.type AS venue_type
FROM s408256.soa_lab2_tickets t
JOIN s408256.soa_lab2_venues v ON v.id = t.venue_id
ORDER BY t.id;
```

Логи: `~/soa-lab2/.runtime/wildfly.log`, `~/soa-lab2/.runtime/nginx.log` и `~/soa-lab2/runtime/payara6/glassfish/domains/domain1/logs/server.log`. Параметры и сгенерированные хранилища ключей находятся в закрытом каталоге `.runtime`, права — только владельцу. Автоматический запуск после перезагрузки Helios не настраивается.

## Выполненные проверки

Для входа без схемы проверены HTTP 308 для GET, HEAD и POST, сохранение пути и параметров, переход на HTTPS с проверкой сертификата, доступность клиента и обоих API. При остановке Payara клиент и Ticket остаются доступны, а Booking возвращает 502. При остановке WildFly клиент недоступен, Payara возвращает 502 для зависимых операций. После перезапусков данные не изменились. TLS передаётся в WildFly без расшифровки в nginx.

После переноса клиента на WildFly проверены загрузка страницы и ресурсов на 28256, VIP-продажа и отмена через HTTPS-прокси, передача ошибок валидации и оба сценария kill -9: при остановке Payara клиент и Ticket отвечают 200, операции Booking — 502; при остановке WildFly клиент недоступен, Payara продолжает возвращать HTTP-ответы. Тестовые записи удалены, исходные данные сохранены.

До удаления вспомогательных скриптов на Helios пройдены 205 HTTP-проверок: CRUD, фильтрация, сортировка, страницы, дополнительные операции, VIP-копия, ошибки и отмена 103 бронирований. Для каждого из сигналов TERM и KILL пройдены 47 проверок API, PostgreSQL и отказов: все поля билета и площадки, SQL NULL, отсутствие записи после ошибки 502 и сохранность данных после завершения обоих серверов. Тестовые записи удалены.

Проверены клиентские сообщения при сетевых ошибках, HTTP 502/503/504 и тайм-ауте, очистка устаревших результатов и восстановление работы после запуска серверов. HTTPS проверен с проверкой сертификатов и имён узлов.

## Структура

```text
common/           JSON, валидация и формат ошибок
ticket-service/   Ticket API, PostgreSQL, веб-клиент, HTTPS-прокси Booking
booking-service/  Booking API, HTTPS-клиент первого сервиса
spec/             исходные спецификации первой лабораторной
deploy/           скрипт запуска, конфигурация nginx и схема PostgreSQL
certs/            публичные сертификаты текущего развёртывания
```
